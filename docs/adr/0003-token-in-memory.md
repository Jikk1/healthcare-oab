# 0003 — Access-токен только в памяти вкладки

- Статус: Accepted
- Дата: 2026-06

## Контекст

SPA-подобные страницы ходят в `/v1` с bearer-токеном. Хранение access-токена в
`localStorage`/`sessionStorage` делает его доступным любому JS — при XSS токен
утекает. Продукт работает с PHI, цена компрометации высока.

## Решение

- **Access-токен** держим **только в памяти** JS-вкладки (`api.js`, поле `state`).
  Он не попадает в storage и не переживает перезагрузку.
- **Refresh-токен** — в `httpOnly`-cookie (path `/v1/auth`), недоступной JS.
- При 401 `api.js` один раз делает тихий `POST /v1/auth/refresh` (cookie уходит
  автоматически) и повторяет запрос с новым access-токеном.

## Последствия

- **+** XSS не может украсть долгоживущий токен из storage; refresh недоступен JS.
- **+** Тихое продление сессии без повторного логина.
- **−** Перезагрузка вкладки теряет access-токен → нужен refresh-роундтрип на старте
  (дашборд/логин делают `ensureSession`). Это приемлемо.
- Смягчение XSS дополняется `escapeHtml` на innerHTML-стоках и строгим CSP ([ADR-0005](0005-strict-csp.md)).
