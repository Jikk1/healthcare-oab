# 0006 — Хеш-цепочка аудита с монотонным `seq`

- Статус: Accepted
- Дата: 2026-06

## Контекст

Соответствие (ФЗ-152, Приказ №965н) требует tamper-evident журнала доступа к PHI.
Каждая запись хешируется с prev-hash, образуя цепочку. Ранняя реализация упорядочивала
цепочку по `createdAt` — при совпадении меток времени (мс) порядок неоднозначен, что
даёт ложные срабатывания проверки целостности и потенциальную гонку при конкурентной
вставке.

## Решение

- Добавлен монотонный `AuditLog.seq` (autoincrement) — цепочка упорядочивается по нему,
  а не по времени.
- Вставка записи (чтение prev-hash + запись новой) — атомарна: per-org **advisory-lock**
  Postgres внутри транзакции.
- Чистые функции `canonicalPayload` / `computeEntryHash` / `verifyEntries` выделены и
  покрыты юнит-тестами.

## Последствия

- **+** Детерминированный порядок цепочки; нет ложных tamper-алертов; конкурентная вставка безопасна.
- **−** Advisory-lock сериализует запись аудита в рамках организации — приемлемо для профиля нагрузки.
- Рантайм с БД (миграция/лок/конкуренция) проверяется CI-интеграцией, не локально.
